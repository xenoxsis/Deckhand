    Deckhand

    A touch panel for Windows that sits on top of your work and never takes focus. Tap a tile to launch an app, raise a window it already has, or type a snippet into whatever you were just working in — the panel never becomes the active window, so the caret stays exactly where you left it.

    What it is

    The panel is a grid of tiles grouped into sections. A tile is one of three things:

    • An app tile — one control split by a line. The wide side goes to a window the program already has (asking which, when there is more than one); the narrow + starts another copy. A folder opens in Explorer; an http(s) address opens as a tab in the browser you are already looking at.
    • A snippet tile — text dropped at the caret of whatever window is focused, either pasted or typed character by character, optionally followed by Tab, Enter or Escape.
    • A folder tile — one per subdirectory of a folder you name, generated at load. Tapping one either opens that folder or types a command template naming it.

    Sections can be tied to profiles — names for the app in front. A section written for your editor is on screen while the editor is focused and gone otherwise, so the panel changes as you move between windows without anything to switch by hand.

    Running it

    The app requires administrator, which is why dotnet run fails with "The requested operation requires elevation". Build it, then start the exe:

    Double-clicking the exe works the same way. Either route puts a UAC prompt in front of you first.

    Why administrator

    Windows refuses synthesized keystrokes aimed at a window running at a higher integrity level than the sender. Without elevation the panel works everywhere except the elevated windows — where it silently does nothing, which is the worst of the options. Elevated, its keystrokes reach everything. The cost is that anything it launches would inherit administrator, so tiles de-elevate what they start by default (see deElevate).

    Local or tablet

    If remote.enabled is on, startup asks where the panel should be: on this laptop (the panel itself) or on a tablet (a small status window here, the panel served to the tablet's browser). With remote.enabled: false the question isn't asked and nothing ever listens on the network.

    The panel's own buttons

    ButtonWhat it does
    🔒Unlock, so the panel can be moved, resized or snapped. Locked is the normal state: a locked panel can't be dragged out of place by a stray finger.
    ↻Re-read the config and rescan folder sections. Saving the file does this on its own — this is the manual, louder version, which also reports config problems in a dialog.
    ⎷Fill this screen, and back again.
    ✕Shut the dashboard down. (In tablet mode the status window's ✕ only hides it to the notification area — the panel keeps serving.)

    The strip at the top left names the app the panel currently thinks is in front, which is also the answer to "why am I not seeing the section I wrote".

    Your first config

    Configuration is one JSON file, dashboard.json, next to the exe — or, in a source checkout, the one beside Deckhand.csproj. The ↻ tooltip names the exact file it read.

    This is enough to be useful. Two always-visible sections, using the apps and snippets shorthand, which each become one section without any grid placement to think about:

    Save it. The panel reloads itself about half a second later — no restart, no rebuild, not even a tap. From there, the things worth reaching for next are sections (to place groups on the grid) and profiles (to make a group follow an app).

    Comments are allowed

    The loader skips // comments and trailing commas, so you can annotate the file even though strict JSON forbids both. Pointing "$schema" at the shipped dashboard.schema.json gives editors like VS Code completion for every key and a squiggle under typos.

    Two files: shared and local

    If a dashboard.local.json sits beside dashboard.json, it is merged over it at load. Keys in the local file win, objects merge a level at a time, and a list or a plain value replaces the shared one outright — half a list from each file would be impossible to reason about.

    The point of the split is that one file travels and one doesn't. Anything with a machine in it — a path with your user name, whether this machine serves to a tablet — goes in the local file, and the shared file stays portable:

    A local file that won't parse costs only itself: the shared file still loads and a warning says what was dropped. When both were read, the ↻ tooltip names both.

    When something doesn't appear

    Most config mistakes are silent by nature — a misspelled key is a key the deserializer skips, and a tile that never appears looks exactly like a tile you didn't write. So the dashboard reads the file a second time against its own model and says what it didn't recognise. Those warnings arrive in a dialog on ↻, in the log, and from --check:

    It prints to the console it was started from (or a message box when there isn't one) and exits 0 when clean, 1 when the report has anything in it — so a script can gate on it. What it catches:

    • Keys the dashboard doesn't know, named with their path ("snipets", layout.colums).
    • A section written for a profile label that no profile has — its tiles could never appear.
    • A profile that can never be reached, because one above it already claims that process unconditionally.
    • A columns/rows range that isn't a number or "1-3"; the section is packed instead of pinned.
    • A titleMatch or split that isn't a valid regex.
    • A tile color that isn't #RGB or #RRGGBB.
    • A source with no folders to scan.

    Two things that are not mistakes and won't be reported: a section written for profiles is invisible until one of them is focused, and a pinned section that overlaps another is left exactly where you pinned it. If a group seems to have a scrollbar it has no need for, compare its rectangle with its neighbours' before anything else.
