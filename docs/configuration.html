    Configuration reference

    Every key the dashboard reads, what it defaults to, and a small example of each. All the examples here are made up — they don't come from anyone's real panel — so they can be copied and edited without leaving someone else's paths behind.

    The top level

    The file is a single JSON object. Every key in it is optional; a dashboard.json containing {} starts an empty panel.

    KeyTypeWhat it's for
    $schemastringPoints an editor at the schema for completion and typo squiggles.
    layoutobjectHow many columns and rows the panel is divided into.
    profilesarrayNames for the apps worth recognising.
    sectionsarrayEvery group of tiles, and where it sits.
    appsarrayShorthand for one always-visible "Apps" section.
    snippetsarrayShorthand for one always-visible "Snippets" section.
    browsersarrayWhich processes count as a browser, for URL tiles.
    remoteobjectServing the panel to a tablet.

    $schema

    Not a setting — a pointer for your editor. With it, VS Code (and anything else that reads JSON Schema) completes key names as you type them and underlines the ones that don't exist. The dashboard skips this key when it checks for typos, so it never reports itself.

    layout

    The panel is a fixed grid, and sections are placed on it by number. There is no size here: the grid is proportional, and the panel's actual size comes from dragging it.

    layout.columns integer ≥ 1 12

    How many columns the width is divided into.

    layout.rows integer ≥ 1 12

    How many rows the height is divided into. Rows share the height equally, which is what gives every group a size fixed by the grid rather than by how many tiles are in it.

    Rows are the sharper trade-off

    Tiles have a minimum height, so a fine row grid buys placement precision at the cost of the smallest useful group. At 12 rows on a 620pt-tall panel a row is about 45pt — less than a tile — so a one-row group scrolls from its very first tile. Budget roughly 2 rows per tile row you want visible, or use fewer rows (3–4) for groups that are comfortable but coarse to place.

    sections

    A section is a bordered, titled group occupying a rectangle of the grid. This is where every tile lives.

    label string

    The group's heading, drawn in small capitals. An empty label draws no heading at all, which is what you want for a group whose tiles speak for themselves.

    profiles array of strings [] — always visible

    The profile labels this section belongs to. It is on screen while one of them is the focused app's profile, and nowhere else. Omit it for a section that is always shown.

    This is the whole of what makes a group conditional, and it's written on the section rather than in the profile so that everything about a group — what its tiles do, where it sits, and when it appears — is in one place.

    columns integer or "from-to" full width, flowing tiles

    See grid ranges below. A plain number is a width to be packed somewhere; a string like "1-3" pins the section to those columns.

    rows integer or "from-to" 1 row

    The same two forms on the other axis.

    tilesPerRow integer 1–24 the section's width in columns

    How many tiles fit across the group before wrapping. A 4-column section fits four 1-column tiles by default; "tilesPerRow": 1 makes a tall narrow list, which is what wide labels want.

    apps array of app tiles

    Tiles that launch or raise something.

    snippets array of snippet tiles

    Tiles that type text into the focused window. Snippets are drawn after apps when a section has both.

    source source object

    Generates one tile per subdirectory of a folder, ahead of any apps and snippets in the same section.

    Grid ranges: pinned or packed

    columns and rows each take one of two forms, and the difference is the whole placement model:

    • A pinned range — "columns": "1-3" — means those tracks, 1-based, wherever everything else ends up. Pinning is what keeps a group in the same place as sections come and go with the focused app.
    • A width — "columns": 3 — means "three wide, wherever it fits". Those sections are packed into the first free gap, scanning left to right and top to bottom.

    Pinned and packed sections mix freely; the packed ones flow around the pinned ones. A few details worth knowing:

    • "1:3" is accepted as well as "1-3".
    • "3-1" is read as "1-3" — a slip, not an error.
    • A range that overhangs the grid keeps its start and loses the overhang, rather than sliding back to fit.
    • Omitting columns does two things: the section is full width, and its tiles size themselves and flow instead of snapping to a tile grid.
    • If pinned sections leave a packed one nowhere to go, rows are appended beyond layout.rows. Every row gets a little shorter rather than a group falling off the bottom.
    Overlaps are honoured, not resolved

    Two sections pinned on both axes keep the rectangles they were given even where those rectangles intersect — moving one would second-guess a config that was explicit. They then draw on top of each other, and the group underneath shows through around the edges. That reads as a bug in the wrong group: a scrollbar a hand's width from the tiles it belongs to looks like it belongs to the small group covering them.

    Group size and scrolling

    A group's size comes from the grid, not from how many tiles are in it. Configure more tiles than fit and the group grows a vertical scrollbar — drag it with a finger — rather than stretching and pushing the rest of the layout around.

    The apps and snippets shorthand

    Top-level apps and snippets lists each become one always-visible section, labelled "Apps" and "Snippets", with no placement of their own. It's the short way in; anything beyond a first config wants real sections.

    profiles

    A profile is a name for an app and how to recognise it. That is all it is: a profile holds no tiles and no placement. It answers "what is the focused window", and every section naming it appears while that's the answer.

    label string

    The name sections refer to, and what the panel's top-left strip shows while this profile is active. Matched case-insensitively.

    match array of strings

    Process names that activate this profile, with or without .exe, matched case-insensitively — what Task Manager's Details tab shows in its Name column.

    titleMatch regex none — any title

    An optional regex the window title must also match. This is how one app is split into several profiles: one editor profile for windows whose title names a particular project, another for the rest.

    First match wins, so order most-specific first

    A profile with a titleMatch can decline a window, leaving a later profile for the same process reachable — which is the only way to split one app in two. A profile with no titleMatch claims its processes outright, so anything below it for the same process can never be reached, and --check says so.

    A titleMatch that doesn't compile matches nothing rather than everything: matching everything would be broader than what was asked for and would shadow every profile below it for as long as the typo lasted.

    App tiles

    An app tile is one control with two sides, divided by a line. The wide side goes to a window the program already has — asking which, when there's more than one — and the narrow + starts another copy. Both sides are always there.

    label string

    The tile's text.

    path string required

    One of three things, and the dashboard tells them apart on its own:

    • A program — a full path, or a bare name that's on PATH ("notepad", "code").
    • A folder — opens in Explorer.
    • An http(s) URL — opens as a tab rather than launching anything. See URL tiles.

    Forward slashes are fine and avoid escaping every backslash.

    args string

    Command line for the program, passed as written. On a URL tile these are browser switches instead (--incognito, Firefox's -private-window), and they only apply when a browser is actually named.

    browser string

    URL tiles only. Omit for the browser you're currently looking at; "default" to always use the system default; a process name like "msedge" to pin the tile to one browser.

    deElevate boolean true

    Launch at normal user integrity instead of inheriting the dashboard's administrator. On by default, and you almost always want that: the dashboard is only elevated so its keystrokes can reach elevated windows, and an editor that silently inherits administrator leaves root-owned files behind in your working copies.

    Set it false on the rare tile that should genuinely run elevated.

    windows array of strings the program in path

    Which processes' windows the wide side goes to. The default is right until the thing you launch isn't the thing that ends up on screen — a launcher that starts something else and exits owns no windows by the time you look.

    git-bash.exe (starts a mintty), git-cmd.exe and wt.exe (starts WindowsTerminal) are handled already. Anything else that starts a fresh copy when its windows are plainly open wants this set.

    span integer ≥ 1 1

    How many of the section's tile columns this tile occupies. Clamped to tilesPerRow.

    color "#RGB" or "#RRGGBB"

    An accent on the tile's outline, on the panel and the tablet alike. On a wall of identical tiles a colour is faster to hit than a label is to read.

    Longer WPF forms like #AARRGGBB are deliberately refused: a browser reads eight digits as RGBA, so the two screens would disagree about what was written.

    icon string — a path

    A picture for the tile. Absolute, or relative to dashboard.json's own folder, with %ENVVARS% expanded.

    The designer's … copies the file it's given into a pictures folder beside the config and writes the relative path, so a layout and its pictures stay one thing you can move. A picture already under that folder is left where it is, an identical one already copied is pointed at rather than copied twice, and a path typed by hand is left exactly as typed.

    png, jpg, gif, bmp, ico, webp and svg — the intersection of what the panel can draw and what a browser can. The tablet is sent the same file, and a picture only one of the two screens can show is a tile that looks different there. tiff is the one left out, and nothing over 2MB.

    svg stays a drawing rather than becoming pixels, so it is sharp at whatever size the tile turns out to be. It has to be self-contained: one that points at another file, declares entities, or carries <script>, a <foreignObject> or an on… handler is refused at load with a line naming which. Pointing within itself (#gradient) is fine; a picture carried inline (data:…) is not, because the drawing package draws nothing for one while a browser draws it — point the tile at that picture instead. Text set in a font is the last thing that can differ between the two screens, so prefer an svg whose lettering was converted to outlines.

    Web Media Extensions component, which a stock Windows 10 or 11 has and some Server and LTSC builds don't. Without it the load warning says so and the tile draws its label, on the tablet too: the panel is what offers a picture at all, so one it can't decode is never sent.

    Windows' webp decoder also reports its frames as carrying no transparency when they plainly do — the alpha is in the bytes, only not in the label — so a logo exported with a transparent background would otherwise draw in a solid black box. The panel relabels those frames instead of believing them, so a transparent webp behaves like a transparent png. An opaque one is unaffected.

    Nothing is extracted, guessed or fetched: the tile draws the file named here and no other. One that's missing, too big, of the wrong type or simply not decodable is named at load with the other config warnings, and the tile draws its label instead.

    iconMode "left" | "above" | "fill" left

    Where that picture goes on the tile:

    • left — a small one at text height, before the label.
    • above — the picture takes the tile, and the label sits underneath it.
    • fill — the tile is the picture, with the label kept as its tooltip.

    The label never goes away, whichever of the three this is: it stays what the tile is called in the log, in a tap from the tablet and to a screen reader. The + is never a picture either — it's the half that opens another window, and on a pair whose wide side has become a logo it's the only thing left with a shape to look for.

    URL tiles and the browser you're looking at

    Handing a URL to Windows opens it in the default browser, which is the wrong one whenever the browser in front of you isn't the default — the tab appears in a window you aren't looking at. So when the focused process is one of the browsers, the URL goes to that browser's own exe with the URL as an argument, which every mainstream browser turns into a tab in its running instance.

    A URL has no window of its own to go back to, so both sides of the tile open the page. Add "windows": [ "msedge" ] to have the wide side raise that browser instead.

    Snippet tiles

    A snippet tile drops text at the caret of whatever window is focused. Because the panel never takes focus, "whatever window is focused" is the one you were just typing in.

    label string

    The tile's text.

    text string required

    What gets inserted. \n is a newline, and it arrives as a real Enter — so an editor's auto-indent applies to each line as it lands, which is usually what you want and occasionally not. Placeholders are resolved at the moment of the tap.

    method "paste" | "type" "paste"

    paste puts the text on the clipboard, sends Ctrl+V, then restores what was there before. Best for anything long or multi-line.

    type synthesizes the characters one at a time. Slower, but it never touches the clipboard and it works in the windows that don't map Ctrl+V to paste — terminal emulators being the usual example, where a paste would put a control character in the prompt instead.

    keys "tab" | "enter" | "escape", space- or comma-separated

    Keys pressed after the text lands, in the order written. Two uses: "enter" to run a command you just typed into a shell, and "escape tab" to hand the rest of the job to your editor's own snippet expansion.

    That second one is the way to a tile that fills in a template rather than a fixed string: inserted text can't select any part of itself, but an editor expanding its own snippet can. Anything else is ignored with a warning in the log.

    span integer ≥ 1 1

    As on an app tile.

    color "#RGB" or "#RRGGBB"

    As on an app tile.

    icon string — a path

    As on an app tile.

    iconMode "left" | "above" | "fill" left

    As on an app tile. There's no + on this kind, so fill leaves the tile as nothing but the picture.

    Editor snippet expansion has one prerequisite

    VS Code needs "editor.tabCompletion": "onlySnippets" before Tab will expand a typed prefix; at its default of off Tab just indents, which looks exactly like the tile having done nothing. Send escape tab rather than tab: typing the prefix opens the suggestion list, and a Tab aimed at that list accepts whatever it happens to have highlighted.

    source — folder sections

    A source fills its section with one tile per subdirectory of a folder you name, so a group of tiles maintains itself as directories come and go. What the tiles do is the command decision:

    • With no command, tapping opens the folder — exactly like an app tile pointed at it, window matching included. A source with nothing but a folders line is a self-maintaining launcher for a projects directory.
    • With a command, tapping types it into the focused window. Give that section profiles naming the windows it types into: the same list both shows the section and is re-checked at tap time, because focus can change between the render and the tap and a command typed into an editor is junk.
    folders string required

    The directory whose subdirectories become tiles. %VARIABLES% are expanded, so a path under the profile can be written without a user name in it.

    exclude array of strings

    Directory names to leave out of the scan entirely, matched case-insensitively.

    split regex none — one flat list

    Deals the folders onto the two sides of a ⇆ switch at the top of the section: names it matches on one side, everything else on the other. Matched case-insensitively, and its first capture group becomes {id} in the commands.

    A pattern that doesn't compile matches nothing, so every folder lands on the "other" side — and --check tells you why.

    The switch is left out when the other side is empty, and which side you're on survives both switching apps and a config reload. It's remembered against the section's label, which is what lets it outlive a reload — so two source sections sharing one label also share their switch side. Give them different labels if you don't want that.

    matchLabel string "matching"

    What the switch calls the folders split matched.

    otherLabel string "others"

    What the switch calls the rest.

    command string none — tapping opens the folder

    Typed into the focused window, with the folder placeholders substituted. Typed rather than pasted, since the usual target is a terminal.

    submit boolean true

    Press Enter after typing, so the command runs rather than sitting at the prompt.

    commands array of {label, command} [] — no ▾

    Extra commands reached by expanding a tile with its ▾, using the same placeholders. Only one tile stays expanded at a time — leaving them all open would push the rest of the panel off a group this tall.

    commandColumns integer 1–8 2

    How many columns the expanded command list is laid out in.

    max integer ≥ 1 24

    Cap on folder tiles. The section heading says when tiles were dropped (PROJECTS (24 of 61)), so a short list is never quietly mistaken for the whole list.

    subtitles string — a file or a glob

    A file of key|text lines, one per line. A folder whose {id} — or, failing that, whose name — appears as a key gets that text as a second line on its tile. A glob like "%USERPROFILE%/notes/titles_*" is allowed so a script can write dated files without coordinating with anyone; on a conflict the newest file wins.

    The format is the entire contract. Anything that can write two fields around a pipe can put subtitles on these tiles, and no file at all just means plain names.

    How folder tiles are ordered

    Most recently used first, then by the folder's own change time. "Used" means tapped: every tap on a folder tile is recorded in %USERPROFILE%\.deckhand_history, and the scan reads it back.

    That record has to be the dashboard's own, because a folder's timestamp only moves when its direct children change — a project you edit deep inside every day can look untouched for months. So the order starts out by change time and learns from use. The file is one seconds␣path line per tap, compacted once it grows; deleting it just resets the ordering.

    Placeholder reference

    All of these are resolved at the moment of the tap, not when the config was written.

    PlaceholderWhereBecomes
    {date}snippet textThe local short date.
    {time}snippet textThe local short time.
    {clipboard}snippet textWhatever text is on the clipboard — empty when what's there isn't text.
    {name}source commandThe folder's name.
    {id}source commandThe first capture group of split; empty when nothing was captured.
    {dir}source commandThe folder's full path, with Windows separators.
    {branch}, {wi}source commandOlder aliases for {name} and {id}, kept so existing configs keep working.
    A snippet that pastes what you copied

    {clipboard} is most useful for wrapping: "text": "`{clipboard}`" puts backticks around whatever you just copied, "text": "> {clipboard}" quotes it. With "method": "paste" the clipboard is read, used, and then restored.

    browsers

    Which process names count as a browser, for the "open this URL in the browser I'm actually looking at" behaviour. The default list already covers the mainstream ones, so this is only worth setting to add something unusual.

    remote

    Serving the panel to a tablet's browser. The short version is here; the whole story, including what stops it being a remote shell, is on the Tablet remote page.

    remote.enabled boolean false

    Whether startup asks "laptop or tablet?". With it false nothing listens, no port is opened and the token is never read. It's the natural thing to put in dashboard.local.json: whether a machine offers its panel to the network is that machine's business.

    remote.listen string "http://+:8787/"

    The prefix to serve on. + means every interface; narrow it to one address to keep it off the others, or to http://127.0.0.1:8787/ when you're reaching it through a tunnel.

    remote.tokenFile string %USERPROFILE%\.deckhand_token

    Where the token really lives: one line, nothing else. Outside the project, so copying the code somewhere doesn't copy the key with it.

    The status window can change this without editing the config: the file is shown under the token, with Change… beside it. A file that already holds a token is adopted rather than overwritten; an empty or missing one is written with the token in use. That choice is remembered in %LOCALAPPDATA%\Deckhand\token-file.json and wins over this key — picking the path this key already names clears it again. New, beside it, writes a fresh token and locks out every paired device.

    remote.token string, 16+ characters

    The token itself — and the one key here that should not be written in dashboard.json, because that file travels with the project. Use tokenFile, which wins over this whenever it has anything in it.

    remote.allowedHosts array of strings

    Names — not addresses — the panel may be reached by: a Tailscale name, a tunnel's hostname. Addresses need no permission; a name does, because what a name points at isn't the dashboard's to decide.

    Files on disk

    PathWhat it holds
    dashboard.jsonThe shared config. Travels with the project.
    dashboard.local.jsonThis machine's overrides, merged over the above. Doesn't travel.
    dashboard.schema.jsonThe schema both files point at, for editor completion.
    %USERPROFILE%\.deckhand_tokenThe remote token, one line.
    %USERPROFILE%\.deckhand_historyFolder-tile taps, for ordering. Safe to delete.
    %LOCALAPPDATA%\Deckhand\Remembered window size and position, and the token file chosen in the status window.
